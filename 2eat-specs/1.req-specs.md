## What it is

What2Eat is a restaurant picker for people who cannot decide what to eat. The user sets **preferences once**, runs **Decide** with location, meal context, budget, and an optional craving, and gets a **short list** of restaurants. Each option shows **why it fits** their saved tastes and constraints, **place facts** from map vendors via places-agent, and a way to **ask follow-up questions** or **open a map**.

Restaurant facts (search, details, geocode, secret-free map links, `sources[]`) come from **places-agent** over **HTTP** with a **caller API key**. The browser never holds map-vendor keys, the caller API key, or LLM keys.

It does not place orders, process payments, or replace restaurant menus, allergen labels, or medical dietary advice. It does not own `plan_itinerary` (where2play + places-agent). It does not scrape 大众点评 / 美团.

## Who it is for

Individuals and small groups who want a fast, constrained recommendation (“what should we eat tonight?”). Office lunch groups, travelers, and households with mixed diets.

## How it fits together

| Piece | Owns | Does not own |
| --- | --- | --- |
| **Web app** (what2eat.food) | Account, preference profile, Decide UX, pick cards, place details dialog, saved/history, preference-match copy, agent chat UX, **browser-local chat transcripts** | Map-vendor adapters, places-agent operator UI |
| **App BFF** (same origin) | Session, which `providers[]` to send, map deeplink choice, preference matching, chat orchestration (stateless per request) | AMAP / Google / Tripadvisor keys; **persisting chat history** |
| **places-agent** (`places-agent`) | `search_restaurants`, `get_place_details`, geocode, `navigate`, card `sources[]`; optional Tripadvisor enrich | Consumer screens, preference profile |

```text
Browser → what2eat same-origin API → places-agent HTTP (/v1)
Browser → what2eat same-origin API → chat (uses same place tools; not MCP from the browser)
```

- BFF uses **HTTP**, not places-agent MCP, from this web app.
- **Caller-driven vendors:** BFF passes `providers[]` (e.g. `["AMAP"]` or `["GOOGLE_MAPS"]` plus optional Tripadvisor enrich).
- **Search vs chat:** Primary lists come from `search_restaurants`. Chat refines or explains using the same HTTP tools; chat is not the only way to search.
- **Chat history:** List chat and place chat transcripts are stored **only in the browser** (device-local storage). The BFF may forward each message for a reply but does **not** write chat history to the database. Transcripts are not synced across devices or tied to the account server-side.

## Locales

All user-facing strings are **i18n keys**. Locales: `EN`, `CN` (`zh-CN`), `HK` (`zh-HK`), `TW` (`zh-TW`). HK and TW catalogs differ. Protocol ids (`AMAP`, `GOOGLE_MAPS`, `TRIPADVISOR`) are not translated.

## Product scope (high level)

Aligned with [`ui-mockup/`](./ui-mockup/) as of the current mock-up pass.

### Shell

- Sticky app header on signed-in pages: logo, Decide / Profile / Saved, greeting + avatar, locale switcher, Log out.
- Public home, auth, and gallery pages: locale switcher where applicable.
- **places.family footer on every product page** (public and signed-in): one centered row — `places.family:` · product marks with logos · copyright.
  - Current product (what2eat.food) is a non-link mark (no underline).
  - Sibling products (where2play.place, places.agent-mate.ai) are underlined links that open in a new tab.
  - Public / no-header pages: footer sits on the picnic cloth with no separate bar.
  - App-header pages: footer chrome matches the header (cream fill + top hairline).
  - Footer Latin type stays on Figtree/Fredoka at a fixed size so EN / CN / HK / TW render the same.

### Home (public)

- Question-led landing, mini placemat preview, CTAs to register or sign in.

### Account

- Open **register** (name, email, gender, age, default location, password + confirm, optional photo).
- **Sign in** with email and password; failed sign-in state.
- **Reset password** via email; **set password** for new account or reset link (including expired link).

### Preference profile

- **Personal information** card: edit name, gender, age, email, default location, optional photo; separate save and last-updated time.
- **Tastes** card: cuisines liked/disliked (preset + custom chips), spice, party size, hard constraints, meal contexts; separate save and last-updated time.
- Budget per person is set on **Decide**, not stored on profile.

### Decide

- **Search criteria:** area or pin, meal context (preset datalist + free text), budget per person, optional craving; submit **Find restaurants**.
- **Results:** short list with last-updated time, summary count, **reshuffle** (same filters, next page of picks), **numbered pagination**.
- **Pick cards:** photo, name, rating, category, address, vendor source ids, fit badge, walk time (when computed), warnings when applicable; actions — Details, Open map.
- **Empty** and **partial vendor** states with actionable copy.
- **List-level agent chat:** floating panel to ask about the current list and filters; transcript restored from browser-local storage on return.

### Place details (dialog)

- Modal on Decide and Saved; close via Close, Escape, or backdrop.
- **Restaurant details:** image + facts from places-agent when available (name, rating, cuisine/category, address, phone, hours or honest missing state, last updated).
- **Why this pick:** preference-match reasons, **also nearby** alternatives from the same search, menu/allergen disclaimer.
- **Place-level agent chat** in the dialog for follow-ups about this restaurant; transcript per place, browser-local only.
- **Open map** (secret-free deeplink from `sources[]`) and **Save**; no Dismiss in the current mock-up.

### Saved & history

- **Saved:** same pick-card pattern; Details, Unsave; empty state.
- **History:** recent decisions with went/skipped, meal context, re-run Decide; reached from Saved; empty state.

### Data honesty

- Show when place facts were last updated; use placeholders when agent fields are missing (hours, photos, etc.).
- Distinguish **place fact** (vendor), **your preference** (profile/decide context), and **agent suggestion** (chat).
- One map-vendor skip must not blank the whole results set.

## Non-goals

- Map-vendor keys, caller API key, or LLM keys in the browser
- Calling places-agent MCP from this web app
- Orders, payments, menus as source of truth, medical allergen advice
- Trip itinerary UX
- places-agent admin UI
- A separate full-page “Why this pick” route (content lives in the place details dialog)
- Server- or database-stored chat transcripts (including cross-device chat sync)

## Success looks like

A user registers, saves tastes and constraints, runs Decide with real place data from places-agent, scans a short paginated list, opens details to see facts and why the place fits, chats to refine or ask about alternatives, opens a map, saves favorites, and can revisit history — without treating the app as a menu or health authority.
