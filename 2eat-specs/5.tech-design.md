# What2Eat — technical design

Implementation design for **what2eat** (`what2eat.food`): a **thin web client + same-origin BFF** that delegates place/map work to **places-agent** over HTTP. Requirements: [`1.req-specs.md`](./1.req-specs.md). Stories: [`3.2eat-stories.md`](./3.2eat-stories.md). Tests: [`4.test-strategy.md`](./4.test-strategy.md). UI: [`2.ui-guidline.md`](./2.ui-guidline.md). Deploy: [`6.deployment-plan.md`](./6.deployment-plan.md). Family trust: [`../../workspace-specs/2.architecture.md`](../../workspace-specs/2.architecture.md).

**Status:** draft — implement one user story to DoD per MVP ([`3.2eat-stories.md`](./3.2eat-stories.md) § MVP plan).

## 1. Goals and non-goals

| Goal | Non-goal |
| --- | --- |
| Thin client: UX, profile, preference match, saved/history in app DB | Map-vendor adapters (places-agent) |
| BFF calls places-agent HTTP with caller API key | Browser calling places-agent or MCP |
| Real Decide via `search_restaurants` + `get_place_details` | Hard-coded restaurant lists in production |
| Chat via BFF → `POST /v1/chat`; history in browser localStorage | Server-stored chat transcripts |
| Four locale catalogs (`EN`, `CN`, `HK`, `TW`) | OpenCC; HK↔TW shared file |
| Same patterns as places-agent admin (Next App Router, Prisma, session auth) | Operator admin UI on this host |
| MVP slices shippable independently | Big-bang single release |

## 2. Architecture principle (thin client)

Per [ADR-001](../../workspace-specs/adr/ADR-001-thin-app-agent-split.md) and [ADR-002](../../workspace-specs/adr/ADR-002-same-origin-bff-trust.md):

```text
Browser (React)
  │  same-origin fetch only
  ▼
what2eat BFF (/api/*)
  │  session cookie auth
  │  Bearer caller API key (server env)
  ▼
places-agent HTTP (/v1/*)
  │  AMAP | Google | Tripadvisor
  ▼
Vendor APIs

Browser localStorage ── list/place chat transcripts (never DB)
App DB ── users, profile, saved, history only
```

**Division of labor**

| Concern | Owner |
| --- | --- |
| Restaurant search, geocode, details, navigate deeplinks | places-agent |
| Tripadvisor enrich flag on search | places-agent HTTP ([ADR-020](../../workspace-specs/adr/ADR-020-http-only-chat-and-enrich.md)) |
| NL place chat tool loop | places-agent `POST /v1/chat` |
| Account, session, profile, tastes | what2eat BFF + DB |
| Fit badge, why bullets, walk-time label, short-list pagination | what2eat BFF (deterministic preference logic) |
| Which map app to open | what2eat client from `sources[]` |
| Chat transcript persistence | Browser localStorage only |

The browser is intentionally **thin**: it renders cards, dialogs, and chat UI; it does not embed business rules for vendor selection or LLM tool loops.

## 4. Runtime shape

Follow places-agent patterns ([`5.agent-design.md`](../../1.places-agent/agent-specs/5.agent-design.md)) where applicable, **without** MCP on this host unless a future ADR adds it.

```text
what2eat (one Node process)
  Next.js App Router
    /                          public home
    /register /login /reset-password /set-password
    /decide /profile /saved /history
    /api/auth/*                session (register, login, logout, reset)
    /api/profile/*             personal + tastes
    /api/decide/*              search, results cache key in session or short TTL server cache
    /api/places/[id]           details aggregation
    /api/saved/*               CRUD saved places
    /api/history/*             decision log
    /api/chat                  proxy to places-agent /v1/chat (stateless)
```

| Path | Auth | Role |
| --- | --- | --- |
| Public marketing + auth pages | None / optional session | Shell, home, account flows |
| `/decide`, `/profile`, `/saved`, `/history` | User session | Signed-in app |
| `/api/*` (except public auth) | Session + CSRF on mutations | BFF |
| places-agent `/v1/*` | Bearer caller key | Server-to-server only |

**Middleware:** protect `/decide`, `/profile`, `/saved`, `/history`, and mutating `/api/*`. Never expose caller key to client bundles.

Stack details: §3. Runtime paths below assume Next App Router + Prisma (PostgreSQL per ADR-023).

## 6. places-agent integration

Reuse the agent HTTP contract from [`8.user-test-cases.md`](../../1.places-agent/agent-specs/8.user-test-cases.md) and [`tests/http-tc-h.test.ts`](../../1.places-agent/tests/http-tc-h.test.ts).

### 6.1 Endpoints used

| BFF action | places-agent call | Notes |
| --- | --- | --- |
| Resolve area text → coordinates | `POST /v1/geocode` | When user types location |
| Find restaurants | `POST /v1/search_restaurants` | Primary Decide path |
| Place facts for dialog | `POST /v1/get_place_details` | Vendor native id from card |
| Map URL | `POST /v1/navigate` or deeplink from card `sources[]` | Secret-free only |
| List / place chat | `POST /v1/chat` | HTTP-only; forward messages + scoped context |

**Not used from what2eat:** MCP, `search_places`, `plan_itinerary`.

### 6.2 Request policy

- BFF sets `providers[]` from product rules (e.g. CN pin → `["AMAP"]`, overseas → `["GOOGLE_MAPS"]`) — caller-driven per [ADR-005](../../workspace-specs/adr/ADR-005-caller-driven-providers.md).
- Optional `enrich: { tripadvisor: true }` on search when configured.
- Pass user `locale` (`EN` | `CN` | `HK` | `TW`) on agent calls that accept it.
- Forward provider skip reasons to UI; never synthesize cards when all providers fail.

### 6.3 Client module

```typescript
// Shape only — implement against agent OpenAPI / TC-H bodies
export async function searchRestaurants(input: {
  near: { lat: number; lng: number };
  query?: string;
  providers: string[];
  locale: string;
  enrichTripadvisor?: boolean;
}): Promise<AgentEnvelope<SearchRestaurantsResult>>;
```

- Read `PLACES_AGENT_BASE_URL` and `PLACES_AGENT_CALLER_KEY` from server env.
- Assert `agent === "places-agent"` on responses.
- Map HTTP errors to i18n keys for the client.

### 6.4 Live vs injected fetch

- **Production / MVP DoD:** real HTTP to places-agent with live vendors.
- **Default CI:** inject `fetchFn` on the client module (same lesson as places-agent adapters) — does not satisfy MVP DoD alone.

## 7. Data model (app DB)

Chat is **excluded** from persistence.

| Entity | Fields (conceptual) | MVP |
| --- | --- | --- |
| `User` | email, password hash, name, gender, age, photo url, default location text, locale preference | 1 |
| `TasteProfile` | likes/dislikes json, spice, party size, constraints json, meal contexts json, updatedAt | 1 |
| `SavedPlace` | userId, vendor source, native id, snapshot json (name, address, rating, sources), savedAt | 2 |
| `DecisionHistory` | userId, place snapshot, area, meal context, outcome (went/skipped), decidedAt | 3 |
| `PasswordResetToken` | userId, token hash, expiresAt | 1 |

**SavedPlace snapshot:** store enough to render pick cards offline from DB without re-searching; refresh details on open via `get_place_details`.

**No tables:** `ChatMessage`, `ChatThread`, or equivalent.

## 8. BFF API surface (conceptual)

| Route | Method | Purpose |
| --- | --- | --- |
| `/api/auth/register` | POST | Create user + empty taste profile |
| `/api/auth/login` | POST | Session |
| `/api/auth/logout` | POST | Clear session; client clears chat localStorage |
| `/api/auth/reset-password` | POST | Email token |
| `/api/auth/set-password` | POST | Token + new password |
| `/api/profile/personal` | GET/PUT | Personal card |
| `/api/profile/tastes` | GET/PUT | Tastes card |
| `/api/decide/search` | POST | Geocode + search + preference match → short list DTO |
| `/api/decide/reshuffle` | POST | Next page/slice same search id |
| `/api/places/[source]/[nativeId]` | GET | Details + why DTO |
| `/api/saved` | GET/POST/DELETE | List / save / unsave |
| `/api/history` | GET/POST | List / record decision |
| `/api/chat` | POST | Body: `{ scope: "list"|"place", messages, context }` → forward to agent |

All responses use i18n **keys** for user-visible errors. Place names/addresses pass through from vendor (Layer B).

### 8.1 Decide flow

1. Load user tastes from DB.
2. Geocode location if needed (agent).
3. `search_restaurants` with providers + optional craving as query hint.
4. BFF computes fit badge, walk minutes (from pin + card location), warning flags.
5. Build why reasons from profile + Decide context (not LLM).
6. Store search metadata (filters, result ids, timestamp) for pagination/reshuffle — server session or short-lived server cache keyed by search id.
7. Return paginated slice to client.

### 8.2 Preference match (BFF-owned)

Deterministic rules — not a separate ranking engine:

- Strong: cuisine like match + budget band + distance under threshold + no hard constraint conflict.
- Partial: one dimension weak (e.g. distance long but cuisine match).
- Weak/conflict: dislike hit, constraint conflict, or closed/long-travel warnings.

Emit reason keys (`eat.why.reason_*` pattern) with interpolation data — not prose in the BFF.

### 8.3 Chat flow (stateless BFF)

1. Browser sends latest user message + **client-held** prior turns (or BFF receives only the new message and client sends rolling window).
2. BFF builds agent context: list scope (area, meal, budget, current result ids) or place scope (place id, facts summary).
3. `POST /v1/chat` to places-agent.
4. Return assistant reply key/text to client.
5. Client appends both turns to localStorage under scope-specific key.
6. **No DB write.**

Recommended localStorage keys (client):

- `w2e.chat.list.{searchId}`
- `w2e.chat.place.{source}:{nativeId}`

Clear all `w2e.chat.*` on logout.

## 10. Security

| Rule | Implementation |
| --- | --- |
| Secrets server-only | Caller key, `OPENAI_*` (if app uses product LLM elsewhere), session secret, Resend |
| Session for user | HttpOnly cookie; CSRF on mutations |
| Input validation | Zod on all `/api/*` bodies |
| AuthZ | User can only read/write own profile, saved, history |
| Map links | Only `sources[].url` / navigate results — never construct URLs with vendor API keys |
| Chat | Rate-limit `/api/chat` per session; truncate message length |
| Uploads | Profile photo size/type limits; store outside web root or object storage |

## 13. MVP implementation order

Aligned with [`3.2eat-stories.md`](./3.2eat-stories.md) and [`4.test-strategy.md`](./4.test-strategy.md).

### MVP-1 — Account & profile (no places-agent)

1. Scaffold Next app + Makefile + Prisma + i18n catalogs.
2. Shell components (`AppHeader`, `FamilyFooter`, locale). Family footer on **all** routes (public seamless vs app chrome).
3. Home, register, login, reset/set password (POST JSON forms — lessons §1).
4. Profile personal + tastes APIs and pages.
5. Playwright MVP-1 journey → DoD (includes footer row + locale size smoke).

**Exit criteria:** New user can register, save profile, re-login; no fixture shortcuts on auth.

### MVP-2 — Decide with real places

1. `places-agent/client` module + env wiring.
2. `/api/decide/search`, preference match, pagination/reshuffle.
3. Decide page + pick cards + empty/partial states.
4. Place details dialog (facts + why); open map; save/unsave + Saved page.
5. Live probe + Playwright MVP-2 journey → DoD.

**Exit criteria:** Real restaurants from live agent; save persists in DB; no `fixture_` ids in probe.

### MVP-3 — Chat & history

1. `/api/chat` proxy to `POST /v1/chat`.
2. Client localStorage chat modules; list panel + place chat in dialog.
3. History API + page; link from Saved.
4. Playwright MVP-3 journey → DoD.

**Exit criteria:** Real agent replies; transcripts survive refresh; cleared on logout; history records decisions.

### TBD — `decide-08` dismiss/cool-off

Defer until UX confirmed; not required for MVP-3 close.
